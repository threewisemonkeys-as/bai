# human_data — training pools built from real human AutumnBench play

`clean_data3` is hand-authored: someone reads `dynamics.txt`, drives the program with
`autumn_drive.py`, and curates slices until every core dynamic is a scored target under
both objectives. This dataset answers a different question — **what happens when the
transitions come from real people instead?** Same learners, same configs, same pool
sizes; only the provenance changes.

Source: `basis_data.zip` → `Human and AI baselines data/cleaned_gameplay_data_filtered.json`
(517 users, 2580 sessions, 43 games). Generated by `offline_learning/human_replay.py`,
checked by `offline_learning/validate_human_data.py`.

## The five things that make human data different

**1. There are no observations.** The logs record only the action stream —
`{"actionType":"noop"}`, `{"actionType":"click","x":C,"y":R}`,
`{"actionType":"reset","seed":"183702"}`. Every frame is RECONSTRUCTED by replaying the
actions through `AutumnBenchEnvWrapper` exactly as `autumn_drive.py` does. Replay is
deterministic, which everything below depends on.

**2. Game identity had to be established.** The study names games semantically; the repo
uses anonymized program IDs. Byte-identical program content gives `ice=BT3GB`,
`disease=DQ8GC`, `ants=S2KT7`. `mario=N2NTD` is fixed by GRID_SIZE 12 (the repo's
`Autumn.cpp/tests/mario.sexp` is a stale 16×16 version) plus the object set
`Mario/Step/Coin/Enemy/Bullet` — human mario clicks span exactly 0–11 on both axes.
`particles=83WKQ` is fixed behaviourally: 83WKQ declares only `(on clicked)`, and the
human `exp_particles` sessions have the 3rd-highest arrow rate of all 43 games (0.238,
sustained to 89% through the session), which is incompatible with a program that ignores
arrows; human `particles` sits in the click-driven cluster.

**3. Clicks are (x=col, y=row).** The log's `{"x":C,"y":R}` becomes the wrapper's
ROW-major `click R C`, which `autumn_env` then transposes to the column-first
interpreter. CSVs store the same row-major string `autumn_drive.py` writes, so
`canon_click` treats human and artificial data identically.

**4. Resets are episode boundaries.** ~700 of 2580 sessions reset mid-phase, and each
reset restarts the program under a NEW seed. Segments are split there; a segment is the
largest run of actions sharing one initial state.

**5. Most of it is nothing happening.** 86% of all logged interactive actions are `noop`
(median session 228 core steps, 45% of sessions >90% noop, 8768 noop runs of length ≥20).
On top of that, inputs the program has no handler for are dead: S2KT7 and 83WKQ declare
only `(on clicked)`, so every arrow press is a no-op; BT3GB has no `up`; N2NTD has no
`down` and its `up`/`clicked` are guarded (jump only when grounded, shoot only with
bullets). Out-of-whitelist verbs are dropped at segmentation — they are exactly what
`load_transitions` would drop anyway.

## Construction

```
human_data/<game>/<variant>/
  drives/{train,test}_d<k>/episode_0/trajectory.csv   full replayed session
  {train,test}_d<k>/episode_<n>/trajectory.csv        2-row slices = the scored targets
  MANIFEST.json                                       provenance + pool stats
  dataset_paths.json                                  ready-made --run/--test-run strings
```

1. **Segment** every session at its resets; keep segments with ≥40 in-whitelist actions,
   capped at 240 steps.
2. **Replay** the 24 longest segments; rank by non-noop count, distinct non-noop verbs,
   and frames changed.
3. **Split by USER.** 3 train drives and 3 test drives from disjoint users, so the
   held-out pool is a different person, not just a different moment.
4. **Probe observability.** For every non-noop step, recompute the counterfactual frame
   that the same state would have reached under `noop`, by re-replaying the prefix.
   O(n²) but only over the chosen drives.
5. **Select targets** (see variants) and emit each as a **2-row slice** — exactly one
   scored target per episode, rows copied VERBATIM. This is what gives exact control of
   the pool size and action balance (`clean_data3_METHODOLOGY.md`: "A 2-row slice yields
   one"); temporal context comes back from the full drive via
   `backfill_context_from_source`, which is why every target is checked to occur exactly
   once in its drive.

### Variants

- **informative** — the mechanical analogue of clean_data3's curation. A target is kept
  only if the action is DISTINGUISHABLE: for a non-noop action the resulting frame must
  differ from the `noop` counterfactual (the action did something waiting would not); for
  `noop` the frame must actually change (passive dynamics visible). Then round-robin over
  action verbs, spreading click locations before reusing any. This is what the reported
  runs use.
- **informative_wc** — same selection, pool sized to worldcoder's reference instead of
  rexpure's (worldcoder has no `--train-n`: pool size sets train AND val, since
  `val_n = min(30, n_total//3)`).
- **raw** — uniform random sample over every in-whitelist transition, no filtering and no
  balancing, so the pool keeps the natural ~80–90% noop composition. The control arm for
  "human data exactly as logged".
- **informative_unified** (2026-08-11) — the informative selection with a FLAT pool of
  60 train / 50 test for every game, `--drive-rank nonnoop`, horizon 1. What every
  reference run in `logs/2026-08-11/human_unified` trained on.
- **informative_unified2** (2026-08-19) — same, `--informative-horizon 8`: the
  waited-instead branch is continued through the human's own next 8 actions, so an
  action whose only immediate effect is latent (dq8gc click=select, paint's colour
  arrows, colour_lines' select-click) is kept when it changes what happens later. Built
  for the 5 original games; no run trained on it.
- **informative_unified3** (2026-08-24) — the recipe for the 15-game selection in
  `experimental_plan.md`: unified2 (horizon 8, nonnoop drive rank, 60/50, seed 1) plus
  `--oov noop`: a human input the program has no handler for is recorded as a `noop`
  tick instead of being deleted, so the replayed timeline (passive dynamics, RNG draws)
  matches what the human actually experienced. logic_gates keeps the plain user split
  (train and test are in-distribution; the question there is whether the learner needs
  to see every switch combination to tell the gates apart). Two drive-selection guards
  were added for it, both no-ops on the original 5 games: **verb coverage** — if a
  whitelist verb that the corpus contains is absent from a split's drives, the best-ranked
  unchosen drive using it is appended (diffusion's top-3 train drives had zero `up`
  presses while its test had 25); **under-fill** — if the drives hold fewer informative
  transitions than the pool needs, further ranked drives are appended (test: users
  outside train) up to `MAX_DRIVES` = 8 (paint's next-3 test segments were one user's
  arrow-only sessions with 30 informative transitions). Command:
  `human_replay.py --game <g> --train-pool 60 --test-pool 50 --seed 1 --drive-rank nonnoop
  --informative-horizon 8 --oov noop --variants informative_unified3:informative`.
- **informative_curated** (2026-08-24) — unified3 recipe with MANUAL drive selection:
  `offline_learning/curated_drives.json` names the session segments per split (user, seed,
  seg_idx + note); listed games use the picks instead of `--drive-rank` (`--ignore-curated`
  reverts). Within-drive sampling is unchanged, so curation is session-level only. The
  guards still backstop under-fill/verb coverage, and guard appends now respect user
  disjointness in BOTH directions (a train append never reuses a test user). First game:
  mario (n2ntd) — both splits carry the coin→ammo→shoot→enemy-death chain the ranked
  pools missed. Candidate sheets for manual review: `scripts/drive_review_sheet.py`.

### Pool sizes are matched to the artificial reference

Measured with `load_transitions` on the reference runs' own `launch.json` paths, so the
only variable between arms is provenance:

| game | rexpure pool | worldcoder pool | test pool |
|---|---|---|---|
| 83wkq | 30 | 104 | 50 |
| bt3gb | 62 | 20 | 50 |
| dq8gc | 30 | 30 | 50 |
| n2ntd | 61 | 30 | 50 |
| s2kt7 | 104 | 104 | 50 |

## Validation gates (`validate_human_data.py`)

1. **Round-trip** — `load_transitions` sees exactly the intended pool and balance.
2. **Backfill** — `backfill_context_from_source` succeeds on every target (rexpure dies
   at startup otherwise). Reported as achieved `avg ctx_prev / ctx_next`.
3. **Verbatim** — each slice row is byte-identical to the drive row with the same `Step`.
4. **Leakage** — train and test drives come from disjoint users, and no
   `(X_t, action, X_t+1)` triple appears in both pools.
5. **Oracle ID ceiling** — re-run the engine from each test target's state under every
   whitelist verb (click at the true location) and count how many reproduce the recorded
   next frame. >1 means the action is not identifiable even by an oracle that knows the
   dynamics. `scripts/oracle_ceiling_ref.py` computes the same number for the artificial
   test sets (inferring their seed by replaying the drive against its own recorded
   frames), so the two are comparable.

## Known limitations

- **Stochastic games replay differently than the human saw.** The engine consumes the
  seed only at RNG-triggering events (S2KT7 first diverges across seeds at step 11,
  83WKQ at 12; BT3GB/DQ8GC never do in 60 steps). Whether the study's seed→RNG mapping
  matches ours is unverified, so for `ants` and `particles` the frames are a valid sample
  of the true dynamics but not necessarily the frames that motivated the human's action.
  Deterministic games (`ice`, `disease`, `mario`) are exact.
- **The informativeness filter can empty an action class.** On dq8gc no human click ever
  satisfied the program's guard (`clicked` fires only on an inactive particle), so the
  pool has no click targets; on n2ntd `click` (shoot) survives once, and `down` has no
  handler at all. These are properties of human play, not bugs, but they mean the human
  and artificial pools do not always cover the same action set.
- **The frame pool for cFD decoys is the whole `--run` pool**, so where the human pool is
  larger than the reference the decoys are drawn from more frames.
